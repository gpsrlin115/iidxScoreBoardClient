# IIDX ScoreBoard 배치 분석 클라이언트 회고 (2026-09-23)

## 기록 범위와 읽는 법

이 문서는 `iidxScoreBoardClient-layout`의 `feat/layout-analysis-youtube` 브랜치에서 진행한 로컬 MP4·YouTube 배치 분석 작업과 Firefox 실사용 문제를 기록한다. 기준 원격 브랜치 `origin/feat/layout-analysis-youtube` 위의 로컬 커밋 22개(`3b3295e`~`199f8a5`), 그 뒤의 클라이언트 변경, 실제 Firefox 진단 JSON과 사용자 재실행 결과를 대조했다. 서버와 sidecar의 이전 조사 결과는 클라이언트의 입력·출력 경계를 설명하는 데 필요한 만큼만 포함한다. 이 문서를 작성하는 시점에 서버·sidecar 코드를 다시 수정하거나 미해결 항목의 현재 상태를 전수 재검증하지는 않았다.

표현을 구분한다. **확인**은 커밋의 재현 기록, 진단 파일, 코드, 또는 명시적인 사용자 재실행으로 뒷받침된다. **추정**은 관측과 맞는 기전이지만 원인 변수를 독립적으로 격리한 실험이 없는 경우다. **미검증**은 합성 입력·모의 응답으로 확인한 범위를 실제 YouTube 공유·서버 대조·정답 배치까지 넓혀 말할 수 없는 경우다. 특히 화면의 `HIGH`는 매처가 반환한 신뢰도 등급이며, 이 작업의 여러 영상·기기·배치에 대해 정확도가 독립 보정됐다는 뜻이 아니다.

브라우저는 파일 또는 사용자가 허용한 공유 화면에서 프레임을 읽고, 게임 영상 영역과 플레이필드의 레인·판정선을 찾는다. OCR로 곡·난이도를 추정하고, 30초의 레인별 노트 시각을 추출한다. 서버가 채보 후보와 매치 요청을 받고 sidecar가 관측 이벤트와 참조 채보를 정렬해 `playedLaneSources`를 돌려준다. 영상·이미지·임시 WebM 자체는 서버 매치 요청에 싣지 않는다. 진단 JSON에는 관측 이벤트·좌표·응답이 들어갈 수 있으므로 사용자 데이터로 다뤄야 한다.

## 1. 채보 계약과 결과 해석이 틀렸던 단계

### 곡 식별자와 채보 식별자 혼동 (`3b3295e`)

처음에는 `songKey`로 후보를 식별했다. 같은 곡의 NORMAL과 ANOTHER가 같은 값을 가지므로 후보를 하나 선택하면 여러 난이도가 함께 선택되고 React 목록 키도 충돌했다. 서버는 `chartId`와 `textageChartKey` 중 정확히 하나를 요구한다. 클라이언트는 채보 단위인 `textageChartKey`를 우선하고 이전 카탈로그 후보만 `chartId`로 대체하도록 바꿨다. 요청 전에 키 형식과 배타 조건을 검사해 400 응답과 하루 10회 매치 쿼터 소모를 막았다. 카탈로그와 수동 난이도는 실제 필터가 걸리는 쿼리 파라미터로 보내고, 지원 범위 밖인 BEGINNER는 제외했다. 서버의 45초 이벤트 한도에 맞춰 이벤트를 자를 때 레인별 개수도 다시 계산한다. 근거: `src/features/layoutAnalysis/candidates.js`, `payload.js`, 커밋 `3b3295e`.

### `status`만 읽어 구체적인 이유를 잃음 (`dcbefaa`)

서버는 `MISMATCH + DIFFICULTY_MISMATCH`, `AMBIGUOUS + REFERENCE_UNVERIFIED`처럼 넓은 상태와 구체적 `reason`을 함께 보낸다. 상태를 먼저 해석한 UI는 서로 다른 실패를 같은 문구로 만들었다. 재대조 버튼도 존재하지 않는 `suggestedSongKey`를 읽어 나타나지 않았다. `reason`을 우선 해석하고, 서버의 `suggestedTextageChartKey`를 사용하도록 고쳤다. `MATCHED`여도 참조가 미검증이면 확정 표시를 하지 않는다. 재대조 성공 후 선택 표시도 실제 대조된 채보로 옮기며, 새 영상을 열면 이전 관측 이벤트를 폐기한다. 배치의 사용자 표시 방향은 `playedLaneSources`이고 `regularToPlayed`는 반대 방향의 내부 값이다. 근거: `src/features/layoutAnalysis/matchResult.js`, `src/pages/LayoutAnalysis.jsx`, 커밋 `dcbefaa`.

## 2. 플레이필드와 OCR의 첫 번째 실패

### 화면 높이를 비율로 가정함 (`ea53700`, `2478175`, `9a1a759`)

초기 검출은 가로 위치와 폭만 찾고 세로 범위·판정선을 화면 높이의 고정 비율로 채웠다. 아레나 모드와 SUDDEN+/LIFT에서는 판정선과 보이는 구간이 달라 엉뚱한 행의 밝기를 읽는다. 여러 프레임에서 얇은 빨간 판정선과 지속되는 레인 경계를 찾도록 바꿨다. 붉은 GREAT 글자를 선으로 잘못 고르지 않도록 행 점유율·두께·아래쪽 위치를 같이 본다. 1~3픽셀 선을 축소하면 색이 희석되므로 판정선은 원본 해상도에서 읽고, 계산량이 큰 가로 격자 탐색만 960픽셀로 줄인다. 커버 이동을 대비해 캡처 중 기하를 재측정하고 안정 구간을 나눈다. 실제 프레임 세 사례에서 플레이필드 x가 470/24/472, 판정선 y가 345/335/383으로 달랐다. 이 값은 고정 비율의 한계를 보여 주지만 모든 화면에서 자동 검출이 성공한다는 증거는 아니다. 근거: `geometryPipeline.js`, `stableSegments.js`, 커밋 `ea53700`·`2478175`·`9a1a759`.

### 로컬 MP4의 첫 장면과 시작점이 게임플레이가 아님 (`3a8febc`)

파일을 열자마자 보이는 화면은 스플래시인데 플레이어에 탐색 컨트롤이 없었다. 좌표 입력란에는 실제 측정값처럼 보이는 기본 비율 좌표가 들어갔고, 일시정지 상태에서 실측하면 같은 장면을 일곱 번 샘플링했다. 분석 버튼은 사용자가 찾아 놓은 위치를 무시하고 파일 0초부터 시작했다. 파일의 20~80%를 여러 시점에서 탐색해 측정하고 재생 위치를 되돌리며, 분석은 현재 또는 측정한 게임플레이 위치에서 시작하도록 변경했다. 측정 전 기본 좌표의 출처를 드러내고 실측 또는 수동 확인을 요구했다. 실제 녹화 4편에서 판정선은 모두 맞았지만 한 영상의 가로 폭은 317픽셀로 잡혀 수동 실측 285픽셀과 차이가 남았다. 자동 탐지는 계속 보정 가능해야 한다. 근거: `videoSampling.js`, `LayoutAnalysis.jsx`, 커밋 `3a8febc`.

### OCR 전체 화면을 제목 한 줄로 합침 (`9a1a759`, `e1dbf27`, `c823c37`)

OCR 결과의 줄바꿈을 지우고 화면 전체를 검색어와 곡명 후보로 보냈다. 스테이지·타이머·아티스트·판정 카운터가 제목에 섞였고, 서버는 쓰레기 문자열에도 짧은 곡명에 높은 점수를 줬다. Tesseract의 줄·단어·신뢰도를 보존하고 화면 상시 표시어와 난이도 단어를 분리했다. 제목의 앞뒤 장식이 자주 오독되므로 온전한 줄과 읽을 수 있는 연속 단어를 최대 다섯 후보로 보낸다. OCR이 사용자가 직접 쓴 검색어를 덮지 않게 했다. 배너가 첫 프레임에 없다는 문제는 파일의 여러 시점을 훑어서 해결했다. `☆`가 `文`으로 읽힌 `Close the World feat.a☆ru` 사례는 라틴 문자 중심 줄에서만 외따로 나온 다른 문자 하나를 뺀 후보를 추가했다. 레벨의 `I`·`l` 보정은 `Lv`/`☆` 뒤 토큰에만 적용해 제목 자체를 바꾸지 않았다. 실제 배너 12장 측정은 제목 6장 성공·5장 오독·1장 미판독, 난이도 3장 일치였다. 이 수치는 Node에서 같은 OCR 자료와 크롭으로 얻은 값이며 실제 브라우저 성공률이 아니다. 근거: `ocr.js`, `ocrText.js`, `ocrLevel.js`, 위 세 커밋.

## 3. 노트를 적게 읽거나 품질을 잘못 판정한 단계

### 3분의 1가량 노트를 놓침 (`9a1a759`, `d333772`)

라벨이 있는 실영상 4편에서 초기 이벤트 수는 sidecar 대비 33~38% 적었다. 이벤트 단위 대조에서는 정밀도가 98~100%라 가짜 양성보다 누락이 문제였다. 첫 5초를 기준선 학습에만 쓰고 노트를 버린 것이 전체의 16~19%를 잃게 했다. 또 평균+3.2표준편차 기준선에 학습 구간의 노트가 섞여 임계값이 과도하게 높아졌다. 모든 프레임을 모아 중앙값·MAD와 하한 4로 판정하도록 변경했다. 라벨 4편에서 sidecar 대비 이벤트 수 차이는 -0.2~-2.6%, 이벤트 재현율 98.2%·정밀도 99.6%였다. 실제 매처도 4/4 배치를 복원했고 모두 HIGH(점수 0.8719~0.9419)였지만 표본은 네 편뿐이다. 근거: `laneEvents.js`, 커밋 `9a1a759`·`d333772`.

### 한 행만 읽는 가정과 채택하지 않은 개선안 (`8225993`, `116f7bd`, `25d2895`)

분석 행이 가림막에 걸리거나 판정선에 너무 가까우면 한 행의 노트가 크게 줄거나 판정 플래시를 노트로 센다. 다섯 상대 높이(0.18·0.34·0.50·0.66·0.82)에서 읽고, 빈 레인 수와 판정선 거리 등을 기준으로 브라우저가 한 밴드를 선택하게 했다. 라벨 4편의 20개 밴드 중 두 개가 실제 매치에 실패했다. 한 번의 픽셀 읽기로 다섯 밴드를 처리해 비용을 억제했다. 프레임 위쪽을 넘어간 수동 영역은 투명 픽셀을 노트 부재로 읽지 않게 잘랐다. 배경 차분·88백분위 밝기 지표도 측정했지만 채택하지 않았다. 백분위는 재현율을 98.2→98.9%로 올리면서 매처 평균 점수를 0.910→0.881로 낮췄다. 노트의 **개수**뿐 아니라 시작 시각의 일관성이 대조에 중요했기 때문이다. 근거: `analysisBands.js`, `laneEvents.js`, 커밋 `8225993`·`116f7bd`·`25d2895`.

### 400과 `AMBIGUOUS`를 구분하기 어려움 (`1a53d55`, `ab6ddf1`)

현재 재생 위치를 원점으로 바꾸는 과정에서 첫 노트가 부동소수 오차 때문에 `-0.0004ms`가 되어 서버의 0 이상 검증에 실패했다. 시작점 근처는 0으로 고정하고, 이벤트·구간의 상하한과 서버 FPS 허용 범위도 계약 경계에서 검사했다. 서버가 돌려준 `AMBIGUOUS / extraction is incomplete`는 매처 진단 수치를 화면에서 버려서 이유를 알기 어려웠다. 매처는 참조 노트 대비 관측 비율 0.4 미만 또는 2개 이상 읽은 건반 레인 7개 미만을 불완전으로 본다. 관측/참조 노트 수·커버리지·사이드 격차·정렬 상관도를 표로 내고 진단 JSON 저장을 추가했다. 잘못된 캡처는 서버 호출 전에 `NOT_SENT`로 거절해 쿼터를 쓰지 않는다. 근거: `observedNotes.js`, `extractionReport.js`, `ResultPanel.jsx`, 커밋 `1a53d55`·`ab6ddf1`.

### 프레임 수와 빈 구간을 혼동함 (`42b26a7`, `2878c89`, `eb38fb4`, `c52a058`)

한 실패 진단은 요청 30초 중 영상 끝의 7.4초만 읽었고 프레임은 81장(10.77fps)이었다. 남은 길이의 기존 5초 하한을 통과했으며, UI는 구간 부족과 프레임 누락을 설명하지 못했다. 남은 길이 확인을 15초로 올리고 실제 종료 이유·도착 프레임·구간 길이를 기록했다. 다음 실험의 11~13fps 재생 끊김은 워커와 영상 디코더 사이 자원 정체가 유력했다. 다섯 밴드를 위해 매 프레임 다섯 번 복사하던 동작을 한 번으로 줄인 뒤 끊김은 사라졌지만 인과를 독립 계측한 것은 아니다. 워커가 느리지 않다는 초기 판단은 잘못됐다. 워커가 프레임을 늦게 닫으면 디코더 버퍼가 묶여 공급 자체가 느려질 수 있다.

그 뒤 재생 30초·워커 평균 15.4ms가 정상이어도 677장, 약 22.5fps만 받는 실행이 있었다. `requestVideoFrameCallback`은 표시 프레임을 따라가며 메인 스레드가 바쁘거나 표시가 멈추면 건너뛸 수 있다. 진행률 갱신을 초당 네 번으로 줄였으나 근본적인 프레임 보장은 되지 않았다. 라벨 4편에서 60fps는 4/4, 30fps는 4/4, 22.5fps는 1/4, 15fps는 0/4 배치를 복원했다. 평균만 보면 연속 공백을 숨기므로 현재 품질 검사는 1초별 최소 30프레임과 최대 공백 250ms를 본다. 이 숫자는 네 편을 솎거나 구멍 내 측정해 정한 방어선이지 보편적인 정확도 보증이 아니다. `9.9초·386장·12.9fps`라는 서로 맞지 않는 옛 표시값도 동일한 프레임 시각으로 다시 계산하도록 바로잡았다. 근거: `captureQuality.js`, `extractionReport.js`, 위 네 커밋.

### 로컬 MP4를 재생 콜백에서 파일 직접 디코딩으로 교체 (`244ee07`, `8c7275d`, `c919f37`, `199f8a5`)

화면 밖·백그라운드·메인 스레드 상태에 파일 분석이 끌려가지 않게, MP4 샘플 위치를 파싱해 선택 구간만 WebCodecs `VideoDecoder`로 워커에서 푼다. 일반 MP4와 조각 MP4를 모두 읽고, 키프레임부터 시작해 표시 시각에 맞는 30초 프레임을 처리한다. 큰 파일의 필요한 바이트만 4MiB 이하 묶음으로 읽고 디코더 대기열을 제한한다. 파일은 구간 안의 예상 프레임 수를 알 수 있어 실제 수와 비교할 수 있다. 이 직접 파서는 유지보수 부담이라는 비용도 남겼다. 실파일·ffprobe 샘플 위치 대조는 24/24, 브라우저 하네스는 Chrome 153에서 48/48, Firefox 156에서 44/44였다. 라벨 4편의 30초 구간은 각각 1800/1800프레임, 최장 간격 16.7ms, 두 브라우저에서 4/4 배치를 복원했다. 성공 결과에도 캡처 요약을 표시하도록 했다. 이 성과는 로컬 MP4 경로의 검증이며 Firefox YouTube 공유의 품질을 뜻하지 않는다. 근거: `mp4/window.js`, `fileFrames.js`, `detector.worker.js`, 위 네 커밋과 `test/fixtures/worker-clips/browser/`.

## 4. YouTube와 Firefox 실사용에서 드러난 연결·좌표·OCR 문제

이 절은 `199f8a5` 이후의 변경과 로컬 조사 기록 `docs/youtube-capture-regression-2026-09-22.md`를 다룬다. 이 문서에 담긴 수정과 운영 배포 여부는 별개다.

### 링크가 보여도 분석 입력은 연결되지 않음

YouTube URL은 iframe만 만들었다. 원본 iframe 픽셀은 클라이언트가 직접 읽을 수 없으므로 별도 화면 공유가 필요한데, 메타데이터 실패 문구와 버튼 상태가 그 절차를 설명하지 못했다. 공유를 허용하기 전에는 실측·OCR·분석이 동작할 수 없었다. 화면 공유의 순서를 명시하고, 실제 첫 프레임 수신을 확인해 연결 완료로 표시하게 했다. 메타데이터 요청 실패는 플레이어 표시와 화면 공유를 막지 않게 분리했다. 잘못된 공유 화면·취소·크롭 실패는 옆에 즉시 오류를 표시하고 트랙을 정리한다. Chrome·Edge 경로는 현재 ScoreBoard 탭을 선택해 Element Capture 또는 Region Capture로 플레이어 영역만 읽는다. 공유 스트림의 프레임은 `MediaStreamTrackProcessor`에서 직접 얻으며 워커 준비 신호 뒤에 스트림을 붙여 시작 프레임 공백을 막는다. 초기 합성 실행에서 준비 이전 391ms 공백 때문에 `NOT_SENT`가 났고, 기준을 완화하지 않고 초기화 순서를 고쳤다. 근거: `capture.js`, `useAnalysisMedia.js`, `analysisRun.js`, 로컬 캡처 조사 기록 `docs/youtube-capture-regression-2026-09-22.md`.

### Firefox에 없는 API를 필수로 요구함

초기 공유 경로는 `MediaStreamTrackProcessor`와 크롭 API를 필수로 요구해 Firefox 화면에 Chrome·Edge 전용 문구가 나왔다. Firefox는 별도 `IIDX 영상 공유` 창을 선택하고, 그 창의 트랙을 30초 동안 메모리에서 VP8/WebM으로 녹화한 뒤 Mediabunny/WebCodecs로 프레임과 캡처 시각을 읽는다. 임시 영상은 서버로 보내지 않고 64MiB 상한·취소·디코더 정리 경로를 둔다. 워커의 지연 로딩에는 Vite 모듈 워커 빌드가 필요했다. Firefox의 공유 설정은 `displaySurface` 대신 `mediaSource`가 오거나 둘 다 없을 수 있어, 명시적으로 부적절한 화면만 거절하고 설정 부재만으로 사용자가 고른 창을 거절하지 않게 했다. 이 기능을 분리하면서 로컬 MP4 파일 선택 버튼의 스타일을 불필요하게 바꿨다가 사용자의 지적 후 원래 클래스로 되돌렸다. 근거: `recordedCapture.js`, `recordedFrames.js`, `streamFrames.js`, `capture.js`, `vite.config.js`, 로컬 Firefox 합성 결과 `test/fixtures/worker-clips/firefox-capture-check/firefox-result.json`.

Firefox 156의 캔버스 공유 하네스는 11/11, 30초에 1,350프레임·최장 공백 42ms였고 Chrome 153의 강제 녹화 경로도 11/11, 1,751프레임·33ms였다. 실제 브라우저의 녹화·디코더·워커는 사용했지만 화면 선택창과 YouTube 영상, 후보·매치 응답은 모의 입력이었다. 이 결과만으로 실사용이 끝났다고 판단한 것이 다음 실패를 늦게 발견하게 했다.

### 실제 Firefox 창 테두리와 안내문이 분석 대상에 섞임

사용자가 실제 Firefox 창을 공유하자 연결은 됐지만 실측은 “플레이필드의 세로 범위를 찾지 못했습니다”, OCR은 `Mozilla Firefox / AJURIKA / Mozilla`를 곡명 후보로 냈다. 합성 캔버스에는 브라우저 테두리·안내문·영상 여백이 없었다. 전용 공유 창의 16:9 영상 바깥 네 모서리에 서로 다른 색의 정사각형 표식을 넣고, 캡처 프레임에서 네 표식의 모양·위치 관계를 검사해 `contentRect`를 찾는다. 표식이 없거나 모호하면 실제 공유 이미지에서 사용자가 영상 사각형을 드래그한다. 정지 이미지와 선택 영역, 파란 레인·빨간 판정선 오버레이를 함께 보여준다. 첫 합성 검사에서는 청록 노트를 표식으로 잘못 읽어 정사각형 연결 성분 조건을 추가했다. 근거: `public/layout-analysis-player.html`, `contentRegion.js`, `CapturePreview.jsx`, `useAnalysisMedia.js`.

실측과 OCR은 `contentRect` 내부만 처리하고, 검출 좌표는 원본 캡처 픽셀로 돌려 워커에 전달한다. 가로 점수 1위 후보가 세로 검증에서 실패해도 다음 후보를 최대 다섯 개까지 확인한다. 공유 창 크기 변경·재연결·수동 영상 영역 수정 시 이전 좌표와 결과를 버린다. 실제 Firefox 공유에서는 사용자가 레인과 판정선 오버레이가 맞는다고 확인했다. 이는 해당 입력의 좌표 시각 정합성 확인이며 모든 영상의 자동 검출 성능을 뜻하지 않는다. 근거: `geometryPipeline.js`, `laneColumns.js`, `useAnalysisMedia.js`, 로컬 실공유 추출 요약 `test/fixtures/worker-clips/firefox-capture-check/firefox-live-result.json`.

### 제목 글자는 있었지만 후보 선택이 버림

영역을 좁힌 뒤에도 첫 Firefox OCR은 `i rr / ANOTHER`로 나왔다. 사용자가 보내 준 OCR 원문에는 `ot A HARD BRAIN y`, 다음 줄 `AJURIKA`, 다음 줄 `ANOTHER`가 있었다. 즉 이 사례는 OCR 엔진이 제목을 전혀 못 읽은 문제가 아니라, 잡음이 붙은 제목 줄을 후보 규칙이 버리고 아티스트나 작은 파편을 고른 문제였다. 공유 영상에서는 제목 줄의 상대 위치·크기·아티스트 줄과의 관계, 여러 프레임의 일치를 사용하고, 줄 구조가 손상된 경우 원문의 제목→아티스트→난이도 순서에서 반복되는 `HARD BRAIN` 핵심 부분을 추출한다. `AJURIKA`를 금지 단어로 등록한 해결책은 아니다. 확실한 제목 근거가 없으면 직접 검색을 안내하고 OCR 원문을 펼쳐 볼 수 있게 했다. 사용자의 실제 Firefox 재실행에서 `HARD BRAIN / ANOTHER`가 표시됐다. 근거: `ocr.js`, `ocrText.js`, `LayoutAnalysis.jsx`, 로컬 캡처 조사 기록 `docs/youtube-capture-regression-2026-09-22.md`.

### 프레임이 충분한데 키 노트가 0개인 30초 분석

사용자가 저장한 실패 진단 JSON `layout-analysis-20260923014812.json`은 `aT4W2rQ19rk`에서 30초·1,620프레임(54.0fps), 최장 공백 80ms, 30fps 미만인 1초 구간 없음, 실처리 35.6초를 기록한다. 그런데 이벤트는 건반 레인 1~7번 각각 0개, 레인 8번에만 3개였다. 클라이언트가 `NOT_SENT`로 차단했으므로 서버 대조가 실패한 사례는 아니다. 실측 좌표는 x89·y228·폭267·판정선508·분석행289로 기록돼 있다. 이 숫자는 프레임 **도착 시각**이 건강함을 보여 줄 뿐, 그 안에 내려오는 노트가 실제로 계속 보였음을 증명하지 않는다.

사용자가 공유 창을 다시 보이게 두고 재실행하자 키 레인 노트가 잡혔다. 별도의 실제 Firefox 공유 검증 요약에는 29.983초에 이벤트 278개, 좌표 x89·y230·폭267·판정선508이 기록돼 있고 사용자가 오버레이 일치도 확인했다. 따라서 이 실패는 좌표가 크게 어긋난 것보다는 공유 창이 최소화된 동안 영상 내용이 갱신되지 않았다는 설명과 맞는다. 다만 실패 당시의 영상 픽셀이나 창 상태를 진단 JSON에 저장하지 않았고, 최소화만 통제한 A/B 실험도 없다. **원인 기전은 유력한 추정**으로 기록한다. 현재 FPS·공백 검사는 정지·반복 화면을 판별하지 못한다. 공유 창을 보이는 상태에서 재생한 재실행은 노트 추출 단계까지 확인됐지만, 자동으로 최소화 상태를 감지·복구하는 기능은 아직 없다. 근거: 위 두 JSON, 사용자 재실행, `captureQuality.js`, `observedNotes.js`.

### 검증 페이지 메시지와 실제 서버 결과를 혼동함

`firefox-real-check` 페이지는 실제 컴포넌트와 공유 창으로 실측·OCR·30초 추출을 수행하지만 `getYouTubeMetadata`, 후보와 `layoutAnalysisApi.match`를 시험용으로 대체한다. “검증 페이지에서 노트 추출까지 확인했습니다. 서버 대조는 실제 분석 페이지에서 실행하세요”는 노트 추출 완료 뒤 매치 단계에 의도적으로 내는 문구다. 이를 배치 복원 성공으로 세면 안 된다. 실제 대조는 로그인·백엔드 8080·sidecar 8765가 연결된 `/layout-analysis`에서 별도로 수행해야 한다. 사용자는 이후 실제 화면에서 결과가 나온다고 보고했지만, 이 문서에 최종 결과 JSON·정답 배치 대조 자료는 없다. 근거: `test/fixtures/worker-clips/firefox-real-check/real.jsx`, 사용자 보고.

## 남은 문제/검증 경계

1. **클라이언트와 서버/sidecar의 변경 범위가 다르다.** 이 클라이언트 워크트리를 푸시·PR로 올려도 서버·sidecar 수정은 함께 들어가지 않는다. 초기 조사에서 카탈로그 제목의 `#색상코드`가 섞인 약 378곡은 400, 짧은 곡명은 무관한 검색어에도 약 0.81점으로 올라옴, 사이드 `UNKNOWN`인 2P 결과는 1P 기준 회전 없이 반환될 수 있음, 영어 서버 오류가 UI에 그대로 보임이 보고됐다. `UNKNOWN` 회전 문제는 `ab6ddf1` 커밋 기록에도 남아 있다. **이번 문서 작성에서는 각 항목의 현재 서버 코드·재현 상태를 다시 확인하지 않았다.** 해결 완료로 간주하거나 클라이언트 PR의 해결 범위에 포함하지 않는다.
2. **Textage 표시 정리는 화면 수준이다.** 결과 화면에서 `Textage 출처` 링크와 SHA-256 표시를 제거하고, `Textage intentionally normalizes some sub-32nd timing differences; event times are for lane matching, not judgement analysis`라는 특정 경고 문자열만 필터링했다(`src/components/layout-analysis/ResultPanel.jsx`). 이는 결과 응답의 `reference`·`warnings` 메타데이터, 참조 검증, 매처의 타이밍 처리 자체를 삭제하거나 바꾸지 않는다. Textage 기준 채보의 미세 시각 정규화 가능성은 여전히 해석상의 한계다.
3. **시각적 유사성과 배치 정답은 별개다.** 이전 `Close the World feat.a☆ru` 사례에서 사용자는 `HIGH` 후보가 Textage의 배치 보기와 비슷하지만 약 11초 부근부터 다르다고 관찰했다. 이 차이가 프레임 검출·시간 정렬·참조 시각 정규화·채보 선택 중 어디에서 비롯됐는지 독립적으로 확정한 자료는 없다. 30초에서 더 길게 읽거나 등급만 보고 정확하다고 단정하지 않는다. 현재 `HIGH` 기준의 정밀도·재현율을 외부 정답 코퍼스로 보정하는 작업이 남는다.
4. **프레임 품질과 내용 품질은 다르다.** 최소화 의심 사례처럼 캡처 시각·FPS·공백이 좋아도 같은 이미지나 노트가 없는 장면이 반복될 수 있다. 공유 창의 재생·가시 상태를 유지하도록 안내하지만, 정지 화면 검출과 자동 재시도는 미구현이다. Firefox 창의 실제 영상 크기·해상도·장식, YouTube 재생 상태와 브라우저 버전이 달라지면 표식 탐지·OCR·실측을 다시 확인해야 한다.
5. **서비스 가동과 배포는 다른 상태다.** 로컬에서 5173·8080·8765를 실행해 실제 결과를 한 번 본 것은 운영 배포나 장기 안정성 확인이 아니다. 클라이언트 PR은 서버/sidecar 변경을 포함하지 않으므로, 호환되는 버전 조합·실제 매치 응답·캡처 진단을 PR 검토와 출시 전 검증에서 별도로 확인해야 한다.
